## What is new

### Control Plane

- **Custom registry credentials:** cluster registration can use a Kubernetes Secret instead of a username/password. Create the secret in every Data Plane namespace where it is needed and follow the [cluster registration instructions](https://docs.tibco.com/pub/platform-cp/1.21.0/doc/html/UserGuide/registering-an-existing-kubernetes-cluster.htm).
- **Hybrid connectivity options:** connectivity can be enabled or disabled for an individual Data Plane. A Data Plane can use a customer-provided ingress or Gateway API controller instead of the built-in HAProxy ingress. This concerns Data Plane hybrid connectivity, not capability Route resources.
- **Registration fields:** when hybrid connectivity is disabled, **Reachable DP URL** must identify the Data Plane `cpdpproxy` service (for example, `http://cpdpproxy.<dp-ns>.svc.cluster.local`) and be reachable from the Control Plane. It is not the application ingress FQDN. Registration also adds route-resource controller/service details, optional proxy and certificate settings, a Fluent Bit service-log setting, and custom Helm-repository options. Review the [1.21 registration guide](https://docs.tibco.com/pub/platform-cp/1.21.0/doc/html/UserGuide/registering-an-existing-kubernetes-cluster.htm) before registering.
- **Native Control Tower (Preview):** a lightweight Data Plane for supported Linux x86_64 hosts, delivered as a Go binary without Kubernetes or containers. It can coexist with Kubernetes Data Planes and is registered as a separate Data Plane type.
- **TESSA write operations:** state-changing operations are disabled by default and must be enabled by a subscription owner. Per-tool safeguards can require confirmation, session approval, or one-time-password verification.
- **Self-hosted MCP Hub:** `tibco-cp-mcp-hub` can be installed into a self-hosted Control Plane namespace and enabled in the Platform Console.
- **Maintenance Mode:** administrators can block user-initiated writes during planned maintenance while reads and internal platform processes continue.
- **System Notification Banner:** administrators can publish notices on login pages independently of Maintenance Mode.

### Capabilities

- **BusinessWorks 6 Containers:** alerts can target all applications or selected applications; process starters can be enabled or disabled for applications deployed with BW 6.12.0 HF-004 or later.
- **BusinessWorks 5 Containers:** Config Management now covers supported non-password Shared Resource and activity fields; process starters can be managed; alerts can target selected applications; Hot Update is supported for supported fields, with a new API.
- **BusinessWorks 5 / Adapters on Control Tower:** a REST API is available under `/cp/bw5/v1/ct`, alongside process diagrams and in-console management of application properties and telemetry settings.
- **EMS:** the provisioning and upgrade wizard is redesigned and opens the GEMS dashboard after successful provisioning.
- **EMS MCP capability:** the EMS MCP capability is available, with one such capability supported per Data Plane.

## EKS requirements and operator notes

- The 1.21 system requirements list Kubernetes 1.35 as certified. Confirm the selected EKS version is supported by both TIBCO for 1.21 and AWS in the target region before choosing a cluster version; generic Kubernetes certification does not establish provider-specific support.
- The official requirements list PostgreSQL 16 with `uuid-ossp` for self-hosted Control Plane and Helm 3.17.0 or later.
- Keep the EKS workshop's Aurora `rds.force_ssl` configuration and EFS/EBS storage prerequisites. Use the Control Plane-generated Data Plane commands when registering a cluster because they include the selected per-Data-Plane connectivity and controller configuration.
- For a custom image registry, follow the 1.21 cluster registration flow for Kubernetes Secret authentication and ensure the secret is present in all applicable Data Plane namespaces.
- For air-gapped or private-registry deployments, use the matching 1.21.0 image manifests and official image-sync scripts; push updated images before starting the upgrade.

## Upgrade from 1.20.0

The official upgrade assistant accepts a deployed Control Plane at `app_version` 1.20.0. Do not use it to skip a minor release.

1. Back up the database, Helm values, and required Kubernetes secrets. Record `helm history` and verify the Control Plane release is healthy.
2. If using a custom image registry, mirror the 1.21.0 images before upgrading. Run the official prerequisite validation script and `helm repo update`.
3. Use [`scripts/1.21.0/upgrade.sh`](https://github.com/TIBCOSoftware/tp-helm-charts/blob/main/scripts/1.21.0/upgrade.sh) and its README. The assistant checks the existing release is deployed at 1.20.0, generates versioned values or runs the Control Plane upgrade, and verifies the resulting release. Its README currently defines no 1.21-specific value transformations; review values and chart documentation rather than assuming old values are transformed.
4. Upgrade the decoupled capability charts after the Control Plane. Use the exact versions in the `control-plane`, `bw`, `flogo`, `developer-hub`, `hawk`, `messaging`, and `be` artifact files.
5. Upgrade Data Plane infrastructure and capabilities from the Control Plane UI. Verify the generated commands and the selected hybrid connectivity/controller options.
6. Confirm all Control Plane and Data Plane workloads are healthy and validate installed chart versions against the artifact manifests.

The assistant requires Bash 4+, yq 4.45.4+, Helm 3.17+ and jq 1.8+ for Helm flows, and kubectl for post-upgrade checks. If `manageDbSchema` is false, follow the official external PostgreSQL schema-management procedure. Do not change the default registry or chart repository during this upgrade.

From 1.19.0, upgrade through 1.20.0 first using the [1.19.0](./v1.19.0) and [1.20.0](./v1.20.0) guidance.

## Known issues to review

- **PCP-24968:** after updating an existing LDAP configuration, reconfigure its LDAP group permissions if users receive Access Denied.
- **PCP-24894:** ActiveSpaces incorrectly appears as assignable for Application Manager and Application Viewer in the user-permission wizard; no workaround is documented.
- **PCP-24555:** the `tibcop` CLI does not accept `--ems-use` for Production EMS provisioning; provision EMS through the Control Plane UI instead.
- **PCP-20136:** the documented cleanup workaround applies only to older Control Tower Data Planes using NGINX Ingress. EKS deployments should review the official issue conditions before applying it.

Review the full [official 1.21.0 known-issues list](https://docs.tibco.com/pub/platform-cp/1.21.0/doc/html/Release-Notes/known-issues.htm) before production changes.
