**TIBCO Platform Control Plane:** 1.22.0 | **Platform:** Amazon Elastic Kubernetes Service (EKS)

## What is new

### Control Plane

- **Resource customization for infrastructure components:** CPU, memory, and storage of infrastructure components on Kubernetes and Control Tower Data Planes can be overridden from a YAML editor on the Data Plane configuration page.
- **On-demand infrastructure components (Control Tower):** a Control Tower Data Plane provisions only baseline infrastructure components when it connects. Additional components such as the Hawk Console, BW Adapter, and MFT adapter are installed from the Data Plane configuration page only when needed.
- **Application Operator permission:** users can start, stop, restart, and scale applications and configure their environment variables, but cannot delete applications. The permission can be scoped to a namespace within a Data Plane.
- **Application log download:** history logs can be downloaded as plain text or CSV and real-time logs as text from the Control Plane UI, without access to the log server. History downloads honor the time range and filters of the History Logs viewer.
- **TESSA with Amazon Bedrock:** TESSA can run model calls on Amazon Bedrock in your own AWS account (previously only a customer-provided OpenAI API key was supported). You can switch between OpenAI and Amazon Bedrock at any time. See "Configuring Amazon Bedrock" in the official documentation.
- **TESSA EMS MCP server:** the TIBCO Enterprise Message Service capability can be queried through TESSA.

### Capabilities

- **BusinessWorks 6 Containers:** new alert categories **Instance Count** and **App Status** (Running, Stopped, Scaling, Unknown); the capability supports the Application Operator permission (start, stop, manual scale, environment variables; no deploy, upgrade, delete, or auto-scale).
- **BusinessWorks 5 Containers:** the same two alert categories and Application Operator support; Zoom In, Zoom Out, and Reset controls for process diagrams on the Processes tab; a new API under API Docs for actionable Hawk methods on application instances that were previously exposed through `/commands` on port 8090.
- **BusinessWorks 5 / Adapters on Control Tower:** RESTful APIs under `/cp/bw5/v1/ct` for applications, domains, machines, monitoring, installed software, plugins, and rulebases, usable from Swagger UI, the CLI, and the BusinessWorks MCP Server. The MCP Server adds read-only tools for BW5 on-premise applications managed through Control Tower.
- **Flogo:** engine variables can use the **password** type (value masked in the UI); `build-tp-deployment` of the Flogo App Build CLI can include connector supplements in the generated `build.zip`.

## Removed features

- **NGINX Ingress Controller:** because the community ended active development, NGINX Ingress Controller usage is removed from TIBCO Operated Control Plane. Customers may continue to use it in their own deployments, but TIBCO no longer officially supports or recommends it with Control Plane and Data Planes. The EKS shared guide keeps its ingress-nginx steps for reference and for existing environments; prefer Traefik or a supported Gateway API controller for new deployments.

## EKS requirements and operator notes

- The 1.22 system requirements list Kubernetes 1.35 as certified (unchanged from 1.21). Confirm the selected EKS version is supported by both TIBCO for 1.22 and AWS in the target region before choosing a cluster version; generic Kubernetes certification does not establish provider-specific support.
- The official requirements list PostgreSQL 16 with `uuid-ossp` for self-hosted Control Plane and Helm 3.17.0 or later (unchanged from 1.21). The Control Plane ingress controllers listed in the requirements are Traefik 3.3.4 and OpenShift Container Platform router; Gateway API controllers listed are NGINX Gateway Fabric 2.3.0, Istio 1.28.2, Traefik `traefik-39.0.7`, and NetScaler (Control Plane) plus GKE Gateway Controller (Data Plane).
- Keep the EKS workshop's Aurora `rds.force_ssl` configuration and EFS/EBS storage prerequisites. Use the Control Plane-generated Data Plane commands when registering a cluster; the 1.22 registration guide text is unchanged from 1.21.
- For a custom image registry, ensure the Kubernetes Secret used for registry authentication is present in all applicable Data Plane namespaces.
- For air-gapped or private-registry deployments, use the matching 1.22.0 image manifests and official image-sync scripts; push updated images before starting the upgrade.

## Upgrade from 1.21.0

The official upgrade assistant accepts a deployed Control Plane at `app_version` 1.21.0. Do not use it to skip a minor release.

1. Back up the database, Helm values, and required Kubernetes secrets. Record `helm history` and verify the Control Plane release is healthy.
2. If using a custom image registry, mirror the 1.22.0 images before upgrading. Run the official prerequisite validation script and `helm repo update`.
3. Use [`scripts/1.22.0/upgrade.sh`](https://github.com/TIBCOSoftware/tp-helm-charts/blob/main/scripts/1.22.0/upgrade.sh) and its README. The assistant checks the existing release is deployed at 1.21.0, generates versioned values or runs the Control Plane upgrade (`tibco-cp-base` 1.22.0), and verifies the resulting release. Alternatively run the documented `helm upgrade` for `tibco-cp-base` with `--version=1.22.0` using your current values.
4. The assistant migrates `tp-cp-o11y` settings: if your 1.21.0 values contain `tp-cp-o11y.capabilities.o11y.default` or `.withResources`, it sets `tp-cp-o11y.capabilities.o11y.overwriteRecipe` from the old `default.overwriteRecipe` (`"false"` if unset) and removes the two old sections; other keys in them (chart versions, `isLatest`, release notes) are dropped so 1.22.0 chart defaults apply. If you upgrade with Helm directly, make the same change yourself.
5. Upgrade the decoupled capability charts after the Control Plane. Use the exact versions in the `control-plane`, `bw`, `flogo`, `developer-hub`, `hawk`, `messaging`, `mcp-hub`, and `be` artifact files.
6. Upgrade Data Plane infrastructure and capabilities from the Control Plane UI, including the observability capability (needed for application log download on existing Data Planes, see PCP-25998). Verify the generated commands.
7. Confirm all Control Plane and Data Plane workloads are healthy and validate installed chart versions against the artifact manifests.
8. Optional cleanup: Data Planes that had Resources configured before the upgrade leave a stale `o11y-exporter.yaml` in `/private/tsc/config/capabilities/platform` on the Control Plane PVC. Nothing reads it, so leaving it has no functional impact. Follow the [official removal procedure](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Installation/upgrading-from-previous-version.htm) and run the commands in a pod that mounts `tsc/config` (for example orchestrator), not in the `o11y-service` pod.

The assistant requires Bash 4+, yq 4.45.4+, Helm 3.17+ and jq 1.8+ for Helm flows, and kubectl for post-upgrade checks. If `manageDbSchema` is false, follow the official external PostgreSQL schema-management procedure. Do not change the default registry or chart repository during this upgrade.

From 1.20.0 or earlier, upgrade one minor release at a time using the [1.21.0](./v1.21.0), [1.20.0](./v1.20.0) and [1.19.0](./v1.19.0) guidance.

## Known issues to review

New in the 1.22.0 known-issues list:

- **PCP-26766:** after you customize the observability environment values in the recipe customization UI and then update the observability resource configuration, the customized values are reset to defaults in the UI and at runtime. No workaround is documented.
- **PCP-25998:** after upgrading the Control Plane from 1.21 to 1.22, downloading real-time or history logs fails with "404 page not found" for applications on an existing Data Plane that has not been upgraded. Newly registered Data Planes are not affected. Workaround: upgrade the Data Plane to 1.22, including its observability capability.
- **PCP-27651 (BW6 Containers):** after upgrading Data Plane infrastructure components to 1.22.0, the Capability Provisioner and the application pod Fluent Bit sidecar show error logs.

Also still listed:

- **PCP-20136:** the cleanup workaround applies only when upgrading Control Tower Data Planes configured with NGINX Ingress Controller.
- **PCP-16403:** after removing `use-forwarded-header:true` from the data plane configmap `dp-config-aws-nginx-ingress-nginx-controller`, the Swagger UI for a BW app endpoint fails to open (relevant to EKS Data Planes installed with `dp-config-aws-nginx`). No workaround is documented.
- **PCP-9344:** if only infrastructure components are upgraded and capabilities are not, existing apps can lose endpoints, monitoring data, and environment-control values. Upgrade capabilities after infrastructure.

The 1.21.0 items PCP-24968, PCP-24894, and PCP-24555 do not appear in the 1.22.0 known-issues list. Review the full [official 1.22.0 known-issues list](https://docs.tibco.com/pub/platform-cp/1.22.0/doc/html/Release-Notes/known-issues.htm) before production changes.
